Every complaint starts from zero

A regulator that acts mainly on complaints sees one file at a time. The pattern behind a complaint, and the work already done on similar ones, sits in records that are held separately and rarely joined.

Use case 1: A complaint arrivesThe costs you don't see

How a complaint is usually handled

In a complaint-led model, the work tends to run like this.

  1. A complaint arrivesabout one agreement, from one creditor.
  2. A file is openedfor that complaint alone.
  3. Systems are searched one by onefor anything related, by hand.
  4. A decision is madeon what that file shows.
  5. The file closesand what was learned stays in it.

The costs you don't see

None of these appear in a caseload report, because each file looks complete on its own.

The same problem, investigated as separate matters

Two complaints about the same adviser are two files. Each is closed on its own facts, and the pattern is never seen.

Linked through shared details, the next complaint opens with the earlier ones already attached. Use case 1, step 4

Findings that stay in closed files

A lookup done last year to identify a business is done again this year, because the answer sits in a closed file.

Recorded once against the business, a finding is there for every later case. Use case 1, step 5

A queue worked in date order

The complaint that points to forty affected households waits behind the one about a late notice.

Ranked by what each complaint connects to, the queue shows where the time matters most. Use case 1, step 6

Harm between complaints

Many people affected never complain. If nothing is looked at until someone does, the harm continues in the meantime.

Patterns in proposals as they are lodged can be found without waiting for a complaint. Use case 2, step 1

Patterns split across administrators

Each administrator sees a handful of proposals from the same source. No one sees all of them.

A view across every lodgement shows the whole group. Use case 2, step 3

Hard to show what limited resources achieved

When work is counted in files closed, it is hard to show that one investigation dealt with forty cases.

Linking actions to the agreements they covered shows the reach of each piece of work. Use case 1, step 7

Three use cases, in the order they become possible

Now

1. A complaint arrives

One complaint about one debt agreement turns out to connect to forty more proposals, two earlier complaints and a finding already on file.

Uses: complaints register, proposal forms, the NPII, AFSA's registers, past investigation records.

 Now

2. One contact, many debtors

The same contact details on unrelated debtors' proposals point to an unregistered business, found without a complaint.

Uses: proposal forms and their contact details, NPII outcomes, AFSA's registers, public business listings.

 Later

3. Who is behind the vote

A personal insolvency agreement passes a creditors' vote. Joined records show the voting creditors were connected to the debtor.

Needs: vote records, director details, statement of affairs, PPSR and exchange records, and authority to share them.

How it builds

  1. Now: join what is already receivedComplaints, proposal forms, lodgements, the NPII and the registers, held as one connected record. Each fact keeps the record it came from.
  2. Next: keep what each investigation learnsLookups, notice responses and outcomes are recorded against the people and businesses they concern, so the next case starts with them.
  3. Later: add sources as access allowsEach new source joins the same structure. Use case 3 becomes possible when vote records and shared data are available.

The structure that holds these records is a graph, because the questions are about connections: who shares a contact, which complaints concern the same group, what was already found. Why graph tests that claim on synthetic data. Hume is the platform built to give analysts that view.
