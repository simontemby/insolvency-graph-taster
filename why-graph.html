Why graph

Every step in the use cases was a question about connections: who shares a contact, which complaints concern the same group, how far a creditor sits from a debtor. Here is how those questions were tested, on synthetic data where the answers were planted in advance. Use case 1 follows a single complaint, so it has no test of its own.

Use case 2: one contact, many debtors

The data holds synthetic debt agreement proposals. In of them, spread across unregistered advisers, the contact phone and email on the form belong to the adviser instead of the debtor. Three advisers use one phone and email. One uses them on only 4 proposals. One rotates three phones and three emails so that no single detail appears more than four times.

As controls, two administrators are the contact for of their own clients' proposals, a listed financial counselling service is the contact for , and proposals come from couples sharing one household phone.

Use case 3 (future): connected voting creditors

In 40 proposals we planted a creditor connected to the debtor who voted yes, at five levels of indirection. The other 60 are controls: 22 where a creditor uses the same tax agent office address as the debtor, 12 where a creditor shares the debtor's surname, 2 where a creditor shares a former address with the debtor, and 24 with no connection.

MethodFlags a proposal when a yes-voting creditor (other than a large lender)…
Rules checkshares a phone, address, email, email domain or bank account record with the debtor, or has the same surname
Graph traversalis reachable from the debtor by a path of up to five relationships through people, companies and those identifiers
Graph with contextis reachable as above, without passing through a registered practitioner or an identifier shared by more than eight people or companies

Traversal alone flags every proposal where a creditor uses the debtor's tax agent office, because the office address links them. The context rule stops at identifiers shared by more than eight entities, which removes those. The two shared former addresses are each used by only two people, so both graph methods flag them. An investigator would want to look at those two.

The query

// yes-voting creditors within five relationships of the debtor
MATCH (d:Person)-[:DEBTOR_OF]->(e:Estate {type: 'pia'})
      <-[v:VOTED {in_favour: true}]-(c)
WHERE coalesce(c.role, '') <> 'generic_creditor'
MATCH p = SHORTEST 1 (d)
  (()-[:HAS_ADDRESS|HAS_PHONE|HAS_EMAIL|USES_DOMAIN
       |HOLDS_ACCOUNT|DIRECTOR_OF|SHAREHOLDER_OF
       |SPOUSE_OF|RELATIVE_OF]-(x)
     WHERE x.regulated IS NULL
       AND coalesce(x.shared_by, 0) <= 8){1,5} (c)
RETURN e.ref, c.name, v.amount, length(p) AS hops, p

One pattern covers every relationship type, at any length up to five, and returns the connecting path as evidence. Removing the WHERE clause on x gives the plain traversal method. In SQL, the same question is usually written as a recursive query over a union of the link tables, with the path rebuilt separately.

        Limits of these tests

        • We generated both the data and the methods. The planted patterns follow tactics AFSA and the courts have described, but how many there are, and how they are arranged, was our choice.
        • In use case 3, we set the threshold of eight knowing what the control cases looked like. The context result shows how the mechanism works. It is not a measure of accuracy on real data, which would need its own test.
        • The use case 3 query has not been run against a Neo4j database for this site. The results come from a Python implementation of the same logic: shortest path of up to five relationships, the same relationship types, and the same filter on every node in the path.
        • In use case 2, the threshold of five proposals was set by us, and the 4-proposal adviser was planted to show where the method fails.
        • Termination rates in use cases 1 and 2 are design choices in the synthetic data, not AFSA figures, and neither test uses them.

        Tests on a static page are one thing. Someone has to do this on a Monday morning, across every case, without writing queries.
